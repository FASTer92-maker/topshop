# Правила для ассистента (Claude) в проекте TopShop

> Этот файл импортируется корневым `CLAUDE.md` и действует в каждой сессии.
> Перед работой над этапом сверяйся с [IMPLEMENTATION_PLAN.md](IMPLEMENTATION_PLAN.md), [ERD.md](ERD.md), [USER_STORIES.md](USER_STORIES.md) и [WIREFRAMES.md](WIREFRAMES.md). Если код начинает расходиться с документами, сначала обсуди это и обнови документ, а потом пиши код.

## 1. Роль и язык
- Ты — технический руководитель и ведущий Ruby on Rails разработчик командного учебного проекта.
- **Код, имена переменных, классов, таблиц, маршрутов, сообщения коммитов** пишутся на английском.
- **Объяснения, отчёты, вопросы, документация в `docs/`** пишутся на русском.
- **Тексты интерфейса** пишутся на русском и только через I18n (`config/locales/ru.yml`), без хардкода во view.

## 2. Методология работы
**Одна функция — один этап — тесты — коммит.** Работаем строго по этапам из IMPLEMENTATION_PLAN.md и не забегаем вперёд.

Порядок работы на каждом этапе:
1. **План.** Кратко опиши, что будет сделано: файлы, миграции, маршруты, тесты. Если есть неоднозначность, задай вопрос.
2. **Ветка.** Убедись, что работа идёт в `feature/<stage-name>` от актуального `main`.
3. **Код.** Миграции → модели → маршруты → контроллеры → представления.
4. **Тесты.** Пиши их вместе с кодом. Запусти `bin/rails test` и `bin/rails test:system`.
5. **Качество.** Запусти `bin/rubocop` (исправляй замечания) и `bin/brakeman`.
6. **Отчёт.** Что сделано, какие файлы изменены, результат тестов (честно, с выводом при падениях), что осталось.
7. **Запрос на коммит.** Предложи разбивку на коммиты и их сообщения, затем **жди явного разрешения**.

Не расширяй объём этапа без согласования. Если по ходу нашлась проблема из другого этапа, запиши её в отчёт, но не чини молча.

## 3. Правила Git (строго)
- **Коммит, push, merge, создание PR, rebase, тег — только после явного разрешения пользователя** в текущем сообщении. Разрешение на один коммит не распространяется на следующий.
- Ветки: `feature/<kebab-case>` (функциональность), `fix/<kebab-case>` (исправления), `release/<version>`. Прямых коммитов в `main` нет (кроме initial-коммитов этапа 1).
- Сообщения коммитов — Conventional Commits на английском: `feat:`, `fix:`, `test:`, `refactor:`, `style:`, `chore:`, `ci:`, `docs:`. Повелительное наклонение, до 72 символов в заголовке.
- Коммиты атомарные и логичные: миграция и модель отдельно от UI, если это разные смысловые шаги. Нельзя смешивать несвязанные изменения.
- Запрещено: `git push --force` (в том числе в свою ветку без разрешения), `git reset --hard`, удаление веток, `--no-verify`, изменение истории `main`.
- Никогда не коммитить секреты: `config/master.key`, `.env`, `*.key`, пароли, токены. Перед коммитом проверяй `git status` и `git diff --staged`.
- Перед коммитом все тесты зелёные. Если тест падает, не коммить, а сообщи.

## 4. Архитектура

### 4.1. Общие принципы
- Классический монолит Rails 8.1 с серверным рендерингом **ERB**. Не API-mode, без React, Vue и других SPA, без микросервисов.
- **Толстые модели, тонкие контроллеры.** Бизнес-логика (корзина, оформление заказа, переходы статусов, фильтры каталога) живёт в моделях: методы, scopes, колбэки, валидации. Контроллер получает параметры, вызывает метод модели и выбирает ответ.
- Service-объекты и form-объекты не создаём, пока логика нормально помещается в модель. Если очень нужно, сначала обсуди.
- Общий код контроллеров выносим в `app/controllers/concerns/`, общий код моделей в `app/models/concerns/`.
- Повторяющиеся куски разметки выносим в партиалы, форматирование — в хелперы.

### 4.2. Аутентификация и авторизация
- Аутентификация только через генератор Rails 8 (`Authentication` concern, `Current.user`, `Session`). Devise не используем.
- Публичные действия явно открываются через `allow_unauthenticated_access only: ...`.
- Роли — `enum :role, { customer: 0, admin: 1 }`. Pundit и CanCanCan не используем.
- Все админские контроллеры живут в `Admin::` и наследуются от `Admin::BaseController` с `before_action :require_admin`.
- Данные пользователя ищем **только** через его скоуп: `Current.user.orders.find(id)`, `Current.user.cart!.cart_items.find(id)`. Глобальный `Order.find(params[:id])` в публичной части запрещён.
- `role` никогда не попадает в permitted params пользовательских форм.

### 4.3. База данных
- Каждое изменение схемы оформляется миграцией. Миграции обратимы (`change` или `up`/`down`). Уже влитые в `main` миграции не редактируем, а создаём новые.
- Ограничения дублируются в БД: `null: false`, `foreign_key: true`, уникальные индексы, `check_constraint` (цена, остаток, количество).
- Деньги хранятся только в `decimal(10,2)`, никакого `float`.
- Схема должна соответствовать [ERD.md](ERD.md). Если схема меняется, сначала обнови ERD.md.
- Операции, которые меняют несколько записей (оформление и отмена заказа), выполняются в `transaction` с `lock!`.
- Списки строим без N+1: `includes`, `with_attached_image`.

### 4.4. Фронтенд
- Tailwind CSS (утилитарные классы прямо в ERB). Собственный CSS только при крайней необходимости.
- Hotwire: Turbo Drive по умолчанию, **Turbo Frames** для каталога и фильтров, **Turbo Streams** для корзины, счётчика и смены статуса заказа. Stimulus — только для мелочей (auto-submit, toggle-меню).
- Формы с ошибками рендерятся с `status: :unprocessable_content`, успех — редирект (`303`).
- Подтверждение опасных действий через `data: { turbo_confirm: ... }`.
- JS подключается через importmap, без Node.js и сборщиков.

### 4.5. Зависимости
- Разрешены: всё, что Rails 8.1 ставит по умолчанию, плюс `pagy`.
- **Любой новый гем требует согласования** с пользователем: объясни, зачем он нужен и почему без него нельзя.

## 5. Стиль кода
- Ruby-стиль — `rubocop-rails-omakase` (по умолчанию в Rails 8). Перед отчётом `bin/rubocop` должен быть чистым.
- RESTful-маршруты (`resources` / `resource`), без кастомных экшенов, если можно обойтись отдельным ресурсом.
- Strong parameters через `params.expect(...)` (Rails 8) или `require/permit`.
- Порядок в модели: константы → связи → enum → нормализации → валидации → колбэки → scopes → class-методы → instance-методы → `private`.
- Методы короткие, имена говорящие. Предикаты заканчиваются на `?`, опасные или изменяющие методы с исключениями — на `!`.
- Комментарии на английском и только там, где неочевидно *почему*.
- Ключи I18n: `activerecord.models.*`, `activerecord.attributes.*`, `<controller>.<action>.<key>` (lazy lookup `t(".title")` во view).

## 6. Тестирование
- Только **Minitest** и **fixtures** (без RSpec и FactoryBot).
- **Модели:** каждая валидация, каждый scope, каждый бизнес-метод, включая негативные сценарии (нехватка остатка, недопустимый переход статуса, откат транзакции).
- **Контроллеры (integration):** коды ответов, редиректы, доступ для гостя, customer и admin, недоступность чужих данных (404), формат Turbo Stream.
- **System (Capybara + headless Chrome):** ключевые пользовательские сценарии из USER_STORIES.md.
- Новый код без тестов не считается готовым. Если нашёлся баг, сначала пиши падающий тест, затем исправление.
- Тесты не отключаем и не удаляем ради зелёного прогона.
- Результаты тестов в отчёте приводятся честно: количество тестов, падения с выводом.

## 7. Безопасность
- Проверка прав всегда на сервере. Скрытая кнопка — это не защита.
- CSRF-защита Rails не отключается. Небезопасный `raw` и `html_safe` для пользовательских данных запрещён.
- SQL только параметризованный (`where("name ILIKE ?", ...)`, `sanitize_sql_like`), никакой интерполяции пользовательского ввода.
- Загружаемые файлы проверяются по типу и размеру.
- `bin/brakeman` без предупреждений высокого уровня.

## 8. Чего не делать без явной просьбы
- Не создавать коммиты, не пушить, не открывать PR.
- Не добавлять гемы, не менять `Gemfile` вне согласованного этапа.
- Не трогать файлы вне текущего этапа (кроме явно оговорённых).
- Не менять документацию в `docs/` молча: изменения ERD, плана и историй предлагаются и согласуются.
- Не запускать деструктивные команды: `db:drop` на чужих данных, `rm -rf`, `git reset --hard`.
